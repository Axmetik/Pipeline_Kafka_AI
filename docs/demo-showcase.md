# Демонстрація Energy Monitoring однією командою

Потрібні Python 3 і запущений Docker Desktop із Docker Compose. Host Python
використовує лише стандартну бібліотеку: ML, PostgreSQL та frontend працюють
у контейнерах. Відкрийте термінал у корені репозиторію:

```bash
python3 -m integration.demo showcase
```

Команда перевіряє Docker, локальну конфігурацію, CSV та контрольні суми
наявної довіреної пари моделей. На підготовленому середовищі Docker build
і створення моделей пропускаються; сумісність перевіряється всередині backend
контейнера. Для чистого clone використовується наявний `prepare`: збірка
відсутніх images, завантаження CSV, підготовка **за незмінними frozen
конфігураціями** у новий ignored каталог. Це може зайняти кілька хвилин і
потребує інтернету. Це не запуск експериментів Stage 3/4/6. Наявні перевірені
артефакти, credentials і дані не перезаписуються.

Якщо потрібно використати наявні trusted артефакти на першому запуску:

```bash
python3 -m integration.demo showcase \
  --hgb artifacts/energy/appliances-hgb-bound-v1/model.joblib \
  --anomaly artifacts/energy-anomaly/v1/bundle.joblib
```

Обидва файли повинні бути сумісні з точними контейнерними версіями бібліотек.
Пошкоджений manifest/модель/CSV не видаляються й не замінюються автоматично.
Непорожній каталог без manifest потребує явної реєстрації довіреної пари
через `prepare --hgb … --anomaly …`. Моделі, `.env.mvp` і dataset не входять у Git.

## Що відбувається

1. З'являється новий `showcase-…` run з узгодженими topic/group. Задані раніше
   `MVP_RUN_ID`, `MVP_TOPIC`, `MVP_GROUP_ID` не повторно використовуються showcase.
2. Попередній worker цього ж Compose project коректно зупиняється перед
   перемиканням context. PostgreSQL/Kafka volumes та історичні результати
   залишаються на місці. Інші Compose projects не зупиняються.
3. Запускаються міграції, bootstrap, Kafka, PostgreSQL, worker, API та Dashboard.
4. Виводиться адреса **http://127.0.0.1:8088** і пряме посилання `/?run=showcase-…`.
5. Починається replay 300 вимірювань із паузою 0,5 с. Відкрийте Dashboard
   одразу: не потрібно чекати завершення команди. Producer працює на передньому
   плані й завершується разом із цією командою.
6. Термінал показує число оброблених measurements, forecasts і score records.
   Завершення оголошується після перевірки **300 / 600 / 900**, відсутності
   дублів/відхилень та DB checkpoint `next_offset=300`.

Replay займає приблизно 2,5 хвилини плюс запуск і обробка черги. Це стислий
показ історичних вимірювань: один крок датасету — 10 хвилин, а пауза producer
лише задає швидкість демонстрації. Це не потік фізичного smart meter.

## Що дивитися у браузері

Без явно закріпленого run Dashboard автоматично обирає найновіший запуск.
Якщо ви раніше вручну обрали старий run, відкрийте надруковане пряме посилання
або оберіть новий `showcase-…` у списку. Оновлення відбувається приблизно кожні
2 с після попереднього циклу; перезавантаження сторінки під час replay не потрібне.

- Основний графік: фактична енергія та HGB20, зіставлені за **target timestamp**.
  RF21 залишається окремим reference для residual detector, не primary forecast.
- IF/AE мають початковий warm-up; Residual потребує 144 попередні інтервали.
  Для короткого replay оцінки можуть залишатися відсутніми. `null` — не нуль.
- Кожен детектор має власну шкалу score й поріг та позначку **experimental**.
  Score не є ймовірністю; threshold episode — не підтверджена несправність.
- Лічильники measurements/forecasts/scores показують прогрес. До 600/900
  входять також записи зі статусом warm-up/null, не тільки числові значення.
- Час датасету показується без timezone conversion. Час вимірювання, origin,
  target, надходження та генерації прогнозу — різні поля.
- `worker_status=unknown` без heartbeat залишається чесним статусом; наявність
  checkpoint не є доказом активності worker.

## Швидкість і повторний запуск

```bash
python3 -m integration.demo showcase --limit 300 --sleep 0.5
```

`limit` — додатне число не більше кількості рядків CSV; `sleep` — скінченна
невід'ємна затримка. Для видимих проміжних оновлень рекомендовано 300 і 0,5 с.
Кожен повтор `showcase` створює новий context, а не повторні доставки в старий run.
Попередні результати залишаються доступними у списку запусків. Останній context
зберігається локально в ignored `artifacts/mvp/showcase-last.json` без паролів.

Не запускайте дві демонстрації одночасно. Короткий daemon-wide lease блокує
конкурентні showcase навіть з різних working copies. Якщо процес був примусово
вбитий, lease не захоплюється автоматично: спочатку переконайтеся, що старої
команди немає, потім виконайте надруковану інструкцію `docker rm …-showcase-lease`.
Це видаляє лише порожній stopped lease-контейнер, не volumes/дані.

## Зупинка й відновлення

- `Ctrl+C` у терміналі showcase припиняє лише producer цієї команди. Уже записані
  дані зберігаються, worker може допрацювати доставлені повідомлення.
- Для зупинки сервісів без видалення даних:

  ```bash
  python3 -m integration.demo stop
  ```

- Перегляд стану/журналів і безпечний restart worker/Dashboard:

  ```bash
  python3 -m integration.demo status
  python3 -m integration.demo logs
  python3 -m integration.demo restart
  ```

Зберігайте ті самі `MVP_COMPOSE_PROJECT`/`MVP_WEB_PORT`, якщо їх змінювали.
Legacy `up`/`replay` зберігають стару семантику й використовують звичайну
конфігурацію `.env.mvp`/environment, а не автоматично останній showcase context.
Для нового показу використовуйте саме `showcase`. Для продовження перерваного
showcase через legacy `up` явно задайте разом run/topic/group із
`showcase-last.json`; не змішуйте context різних запусків. `restart` не змінює
context наявного контейнера. Не запускайте lifecycle-команди паралельно із showcase.

Якщо Docker недоступний під час переривання, автоматично підтвердити зупинку
producer неможливо: команда надрукує його **точну** назву та `docker stop …`.
Після відновлення Docker виконайте цю інструкцію перед новим showcase.
При зайнятому іншою системою порту задайте, наприклад, `MVP_WEB_PORT=8089`;
чужі сервіси не зупиняються. Не видаляйте volumes для виправлення помилок.

## Компоненти простими словами

| Компонент | Роль |
|---|---|
| Producer | Читає історичні вимірювання та надсилає їх із заданою паузою |
| Kafka | Зберігає послідовність повідомлень між producer і worker |
| Worker | Перевіряє вимірювання, будує прогнози й experimental scores |
| PostgreSQL | Зберігає результати, історію та checkpoint для відновлення |
| FastAPI | Надає Dashboard read-only доступ до збережених даних |
| Dashboard | Показує графіки та періодично отримує нові результати |

Сервіси залишаються локальними: назовні не відкриваються Kafka/PostgreSQL/API.
Змінено лише оркестрацію запуску; ML, thresholds, DB transaction→Kafka commit,
recovery та результати попередніх експериментів залишаються незмінними.
