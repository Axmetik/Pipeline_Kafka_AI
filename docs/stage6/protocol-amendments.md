# Protocol amendments and preflight observations

## A1 — before the primary series

The first preflight failed before any containers started: uppercase `T` in the generated Compose project ID was rejected. The failed run manifest/log is retained; IDs now use lowercase `t`. No measurements from that attempt exist.

Overhead off-trials use the original worker entry point, no independent DB observer and no DOM telemetry callback; the ordinary browser dashboard and external resource sampler remain in both arms. Both arms retain the small producer correlation ledger. Therefore this estimates incremental worker/DB-observer/DOM instrumentation overhead, not the absolute overhead of every external measurement tool. Baseline worker durations cannot be obtained without instrumenting that baseline: compare completion throughput instead and report instrumented worker duration separately. No synthetic reduction of measured times.

Completion overhead is measured from the first measured producer send to the controller observing the final committed count (100 ms observation cadence). It includes the drain-observation uncertainty; per-message commit throughput is available only in instrumented trials. Freeze model output parity and report the three individual pairs, median and range. These short trials characterize overhead imprecisely; a large or unstable effect requires investigation, not an unqualified zero-overhead claim.

Resource sampling records actual timestamps. Docker CLI stats may deliver samples less frequently than the nominal 1 Hz target; report realized cadence, rather than asserting a precise 1 Hz rate. Browser callback marks React DOM layout commitment, not the end of Recharts animation or display scanout.

The first overhead preflight completed business processing and integrity validation, but its summary parser rejected Docker's compact RAM string (for example `100MiB`). The parser was corrected and cleanup made unconditional; raw data remain available. This unpaired preflight is retained separately from the registered three complete overhead pairs.

## A2 — pilot diagnosis, before the primary series

The three initial 150+100 overhead pairs were too short for stable throughput estimates (one baseline duration was more than twice another). One worker clock sample showed a 14.7 ms epoch/monotonic discrepancy. Preemption between clock reads is a hypothesis, not a demonstrated clock step. Those raw trials are retained. New telemetry brackets every epoch read with two monotonic readings and records the read uncertainty; clock-step checks subtract that uncertainty and still reject uncertainty above 10 ms.

Register a second overhead campaign `overhead-v2-{1,2,3}`, each with 300 warm-up + 600 measured records, the same on/off order, source, artifacts and processing. Use one controller monotonic clock from the observation of the first measured publication ledger entry to observation of the final DB count, avoiding an unsynchronized host/VM epoch subtraction. Start observation cadence is 10 ms; final DB-count polling is 100 ms plus request time. Keep the initial campaign separate, with no deletion or rewriting of measurements. No primary runs have started. The 5% investigation rule still applies. Recovery readiness is an observed upper bound: the first post-restart committed record appears in the asynchronous ledger after Kafka acknowledgement, plus the controller's 10 ms observation cadence and filesystem scheduling.

Resource collection for the primary/API/recovery series discovers all current containers of the unique evaluation project on each sample, including the DB observer, browser, transient replay and HTTP clients. Very short-lived containers may finish between samples; these are not treated as having zero CPU/RAM. Resource CPU/RAM summaries use the controller's measured window; Docker CPU percentages have their own preceding averaging interval. No claim of physical-device latency or CPU power/temperature measurement is made.

## A3 — overhead investigation, before the primary series

Campaign v2 throughput overhead was approximately 9.51%, 3.16%, 32.94% in the three registered pairs (median 9.51%). All observations are retained; no primary runs were released. The writer flushed whenever its queue became empty, often once per message/poll. This causes frequent shared-filesystem operations, even though outside the processing thread; causality for the observed slowdown has not been established.

Register campaign v3 with the identical three pair orders and 300+600 records. Change only telemetry buffering to at most one scheduled flush per second, with immediate background flush for the first post-start/recovery committed message and clean shutdown. Queue loss remains explicit. Start timing now observes a single small first-publication-ack marker written once per phase in both arms; it no longer depends on periodic ledger flushes. This marker is outside the recorded publication-ack span. Readiness-after-restart uses the immediate first-message flush, so recovery detection is not delayed by the one-second general buffer. No ML or DB/checkpoint behavior is changed. The registered primary design remains 300+3600, five repetitions per mode.

## A4 — local telemetry volume and complete environment cleanup

V3 buffering alone did not establish overhead below the investigation budget. It is not evidence that shared-filesystem flushes caused the observed throughput differences. Register campaign v4 (same 300+600 records, three on/off pairs, same order and 50 ms visibility observer). Store bulk telemetry in a fresh Docker-local named volume in BOTH arms, export it to `docs/stage6/raw` only after the timed window and all writers stop. Only small readiness/stop/first-ack/first-resumed-record control markers cross the host shared filesystem. This tests the shared-filesystem hypothesis without changing ML, SQL transactions, Kafka commits or observation cadence. Preserve a volume if export fails, rather than deleting unexported raw data.

One v3 off-attempt failed before publication because Docker address pools were exhausted by unused evaluation `tools` provisioning networks. It is retained and explicitly rerun under a new context. Cleanup now selects the tools profile as well; only unused networks whose Compose project IDs match this harness's `s6-` namespace were removed. Production/demo networks and volumes were preserved. This is an evaluation-infrastructure failure, not evidence of message loss in the worker.

Before the primary series, repeat all three short pilot modes under the final Docker-local telemetry policy, retaining the `pilot-v4` label separately from the original pilot. Run a separate `pilot-recovery-v4` using 150+60 records. Primary release requires these final correctness checks, three v4 overhead pairs, preserved forecasts/scores/episode continuity after restart and successful clock/span/correlation validation. Backend/browser logs use the Docker-local volume; the common external resource sampler continues to write its low-frequency host CSV/JSONL. API replay load waits for the first measured publication marker after its own 50-request/client warm-up, and reports the observed overlap count.

## A5 — verified shared monotonic clock domain

V4's third on-trial was retained as a failed timing validation despite complete business integrity: both producer and worker showed the same approximately +11.532 ms CLOCK_REALTIME correction across the warm-up/measurement boundary. Bracketed read uncertainty was below 0.1 ms, so this was not explained by a wide clock read. Do not rerun until an epoch-clock correction happens not to occur.

Register v5 before its execution: keep epoch readings as diagnostic wall times, but compute producer→worker and DB-availability→DOM latencies in the verified Docker VM CLOCK_MONOTONIC domain. Before every run compare worker, API and tools kernel boot ID, `/proc/self/ns/time` and `get_clock_info('perf_counter')`; refuse incompatible domains. Each producer/worker/observer emits its domain identity. These are separate processes but share a checked kernel clock; this assumption is explicitly limited to this single-host Docker experiment and is not valid for distributed physical devices.

Producer emits send monotonic ticks; worker emits DB-ack monotonic ticks; observer emits lower/upper visibility monotonic bounds. Browser exchanges bridge its `performance.timeOrigin + performance.now()` timeline to the API's shared monotonic ticks using 10 exchanges at start/every 60 s/end. Preserve RTT/2 uncertainty and reject synchronization uncertainty above 10 ms. Wall-clock steps remain reported, but do not invalidate monotonic spans merely because they occurred between phases. No historical dataset time is used. Local spans, source/model bindings, algorithms, database transactions, Kafka offsets and buffering are unchanged.

V5 repeats the same three 300+600 overhead pairs and all three 150+60 short pilot modes, plus recovery. V1–V4 observations and failures remain available separately. Primary counts, five-repeat schedule and API/recovery design remain unchanged.

One v5 on-attempt failed during bootstrap before replay. Compose recorded exit 1, but that early harness version did not retain the exited bootstrap container's own logs before cleanup; its exact cause is unknown. Do not attribute it to model quality, Kafka readiness or data loss without evidence. The attempt remains failed and a new context resumes only that missing pair member. The harness now captures bounded service logs on failure before cleanup and redacts known secrets and PostgreSQL connection URLs. No retry or change to the production bootstrap/worker was introduced.

## A6 — visibility-sampling cost/precision tradeoff

V5's first two complete overhead pairs still exceeded the 5% investigation threshold. The final pair is retained as well; do not select a favorable subset. Register v6 with the same three pair orders and 300+600 records, changing only the independent visibility observer cadence from 50 ms (20 queries/s) to 200 ms (5 queries/s). The observer is instrumentation rather than part of the product. This explicitly trades finer DB-availability bounds for less observer load; freshness remains interval-censored, now typically spanning at least 200 ms plus query/scheduling time. Browser polling remains the existing two seconds. Do not compare freshness midpoint precision across campaigns without these bounds.

Final correctness pilots and recovery pilot use `v6`. Shared monotonic-domain checks, background buffering, artifact bindings, primary run counts/order and all ML/transaction/checkpoint semantics remain unchanged. Any performance benefit from this change must be reported as an instrumentation tradeoff, not a worker optimization.

## A7 — stop rule after instrumentation diagnosis

Stop instrumentation tuning after the registered three v6 pairs, regardless of whether their estimate is favorable. Earlier campaigns remain commissioning diagnostics and are not pooled or cherry-picked as the final overhead estimate. The original 5% rule was a report-and-investigate trigger, not a product SLA or a user-specified maximum. Its initial code gate interpreted that rule more strictly than the protocol text.

If the final v6 median exceeds 5%, release requires a published investigation tied to those exact six run IDs and the unmodified measured percentages. The report must state that primary latency/throughput are instrumented-system results, preserve the budget-exceeded flag, provide all three overhead differences and their range, and make no uninstrumented SLA claim or numerical subtraction. The investigation must document output parity, telemetry loss, CPU samples, buffering/storage/observer tradeoffs and remaining uncertainty about causality. An explicit evidence record can close the investigation; it cannot change measurements or the 5% trigger. No further favorable resampling or optimization campaign will replace v6 for this decision.
